# Журнал інженерних рішень

## ADR-01. Залишити три наявні проєкти

- **Контекст:** репозиторій уже має Core, App і Tests; повне розділення на чотири збірки потребувало б міграції попередніх лабораторних робіт.
- **Розглянуті варіанти:** окремі Domain/Application/Infrastructure; або три проєкти з окремими просторами імен і каталогами.
- **Рішення:** залишити три проєкти, а контракти й реалізації розділяти структурою Core.
- **Наслідки:** менше змін у рішенні й сумісність із попередніми роботами; мінус — компілятор не гарантує напрям залежностей усередині Core, тому потрібен архітектурний тест.
- **Статус:** прийнято.

## ADR-02. Зберігати навчальні записи у JSON, а не лише в пам'яті

- **Контекст:** демонстраційні дані мають бути відтворюваними після перезапуску; база даних умовами курсу не потрібна.
- **Розглянуті варіанти:** пам'ять; CSV для кожної сутності; один JSON із вкладеними колекціями.
- **Рішення:** використовувати JSON-файл із масивами слухачів, курсів, груп і зарахувань.
- **Наслідки:** структура читається людиною та зберігає зв'язки; мінус — файл читається і записується цілком, тому це рішення підходить для навчального обсягу, але не для великих сховищ.
- **Статус:** реалізовано в `JsonEnrollmentRepository`; повторне завантаження даних перевіряється окремими тестами сховища.

## ADR-03. Використовувати власний доменний виняток для порушень правил

- **Контекст:** стандартний InvalidOperationException не дає відрізнити порушення бізнес-правила від помилки стану програми.
- **Розглянуті варіанти:** InvalidOperationException; власний DomainRuleException; тип Result для кожної операції.
- **Рішення:** використовувати DomainRuleException із кодом правила для очікуваних доменних відмов, а ArgumentException залишити для некоректних аргументів на межі.
- **Наслідки:** прикладний шар може показати зрозуміле повідомлення та записати Warning; мінус — треба підтримувати каталог кодів правил і не перетворювати кожну помилку на виняток.
- **Статус:** реалізовано в `EnrollmentService`; очікувані відмови мають код правила та записуються як `Warning` через `IAuditLogger`.

## ADR-04. Не виділяти окремий Infrastructure-проєкт на цьому етапі

- **Контекст:** потрібне файлове сховище, але репозиторій має компактну навчальну структуру.
- **Розглянуті варіанти:** окрема збірка Infrastructure; адаптер у Core/Infrastructure; зберігання безпосередньо у Program.
- **Рішення:** адаптер реалізує інтерфейс репозиторію й розташовується окремо від доменних сутностей; Program відповідає за його створення.
- **Наслідки:** сервіс не знає формату JSON; мінус — фізична межа не контролюється посиланнями проєктів.
- **Статус:** структура `Core/Infrastructure` реалізована; напрям залежностей перевіряють тести `ArchitectureDependencyTests` і `DomainAndRepositoryBoundaryTests`. Обмеження: перевірка виконується на рівні збірки/просторів імен, оскільки шари Core не винесені в окремі проєкти.

## ADR-05. Застосувати політику пакетної ціни

- **Контекст:** варіант 17 вимагає знижку за пакет курсів, але числові ставки в таблиці варіантів не визначені.
- **Розглянуті варіанти:** фіксована знижка; ставка за кількістю курсів; знижка за сумою замовлення.
- **Рішення:** 0 % для одного курсу, 5 % для двох, 10 % для трьох і більше.
- **Наслідки:** правило легко тестувати параметризовано й замінювати іншою реалізацією; мінус — ставки є припущенням, а не числом із методички.
- **Статус:** реалізовано; ставки слід погодити, якщо викладач задав інші.

## ADR-06. Враховувати лише активні зарахування в місткості

- **Контекст:** відрахований або завершений слухач більше не займає місце в поточній групі.
- **Розглянуті варіанти:** рахувати всі записи; рахувати лише Active; вести окрему історію зайнятості.
- **Рішення:** у поточному звіті рахувати тільки Active.
- **Наслідки:** поточна місткість відображається коректно; мінус — звіт не є історичним аналізом заповнення.
- **Статус:** реалізовано.

## ADR-07. Відмовитися від бази даних і вебінтерфейсу

- **Контекст:** завдання вимагає консольний .NET-застосунок і дозволяє пам'ять або файл JSON/CSV.
- **Розглянуті варіанти:** SQL-база й вебінтерфейс; консольний застосунок із файловим сховищем.
- **Рішення:** не додавати БД, вебсервер або графічний інтерфейс.
- **Наслідки:** рішення залишається в межах навчального завдання й не потребує розгортання; мінус — немає багатокористувацької роботи й віддаленого доступу.
- **Статус:** прийнято як свідома відмова.
